# Changelog

## Unreleased

### Fixed

- **Only the owner can give an entity away.** `TimestampedMixin.set_owner()` asked nobody: a caller refused a write could call `set_owner(<own id>)` on the same instance, and the next write passed ([#51](https://github.com/smart-social-contracts/ic-python-db/issues/51)). It is now a write: refused with `PermissionError` to a caller who does not own the entity (any caller may while it has no owner yet), and stored at once, with the caller as the updater. Before, the transfer was kept in memory until the next save, which only the new owner could then make.
- **A write the owner check refuses changes nothing.** The check ran in the save that ends a write, after the field's hook had run, its value had changed in memory and its index entry, sorted entry or relation's reverse index had moved. A caller refused a write could still move another caller's row out of `find_by`, up in `top_by`, or into their own team's members. Setting a field or a relation, and adding to or discarding from a `ManyToMany`, now check first. A write to a row stored by newer code (after a rollback) is refused the same way.
- **Only the owner can delete an entity.** `delete()` checked no owner: any caller could delete a `TimestampedMixin` row. It now raises `PermissionError`, before the `on_event` hook runs.
- **`deserialize()` no longer takes the owner, creator and updater from the data** ([#52](https://github.com/smart-social-contracts/ic-python-db/issues/52)). An import stored the `owner`, `creator` and `updater` the data named, and on an update they stayed as plain attributes that shadowed the mixin: the row kept the imported owner, and a later `set_owner` was not stored. These and the two timestamps are now ignored on a class with the mixin, unless the class declares a field of that name. The caller claims a new row and is the updater of an existing one, as on any other write.
- **A missing caller id or owner is refused** ([#53](https://github.com/smart-social-contracts/ic-python-db/issues/53)). The mixin reads no owner as "not claimed yet", which anyone may write. `set_caller_id(None)` made every save claim the row again and move its creation time, and `set_owner(None)` opened the row to every caller. `set_caller_id`, `as_user` and `set_owner` now raise `ValueError` unless given a non-empty string.
- **A row that holds the default of an indexed or sorted field is in its index** ([#44](https://github.com/smart-social-contracts/ic-python-db/issues/44)). Index entries were written only when an assignment changed a value, and a default is never assigned: `find_by`, `count_by`, `page_by` and `top_by` silently left out every row that held the default (an `"open"` status, a score of 0), and passing the default explicitly did not help. A new entity is now filed in its field and sorted indexes once its constructor has applied every argument, with the defaults of the others. Rows stored before are not: see Upgrading.
- **A constructor that raises leaves nothing behind** ([#43](https://github.com/smart-social-contracts/ic-python-db/issues/43)). An argument refused after an indexed one left that field's index entry, the id counter, and the reverse-index entry of any relation argument before it: `count_by` and a relation's `len()` counted a row that did not exist. Index entries are now written only after the row is saved, the links of relation arguments are taken back, and the id is given back unless another entity took a later one meanwhile.
- **Alias entries are kept in step with the rows** ([#46](https://github.com/smart-social-contracts/ic-python-db/issues/46)). Renaming a row left its old alias resolving to it; a second row with the same alias took the entry over; deleting that row then left the first one unfound by its alias. A rename now removes the old entry, a value another row holds is refused with `ValueError` (on creation and on rename, before anything changes), and `delete()` removes an entry only if it names the deleted row. An entry whose row is gone, or no longer holds the value, is stale and is taken over. `deserialize()` keeps aliases the same way.
- **An entity held across a message boundary no longer writes back old values** ([#47](https://github.com/smart-social-contracts/ic-python-db/issues/47)). The identity map is emptied when a message starts, so code that loads an entity, awaits another canister and then sets a field holds an instance no load returns. Its save wrote every field it held, putting back what other messages had changed in the meantime (a payment recorded while the call was out was undone). Such an instance now checks the stored row before it writes: unchanged, the write goes through; changed or deleted by another message, it raises `StaleEntityError`.
- **A `deserialize()` that raises half-way changes nothing** ([#54](https://github.com/smart-social-contracts/ic-python-db/issues/54)). A field refused by its type, its validator or a hook left saving switched off on that instance for the rest of the message, so the next write to it returned normally and was not stored; the fields merged before it had moved their index entries although the row was never saved. The merged fields and their entries are now put back, and saving is on again.
- **A `Float` field takes an `int`, and `Integer` and `Float` fields refuse a `bool`** ([#48](https://github.com/smart-social-contracts/ic-python-db/issues/48)). `price = 5` raised `TypeError`; an `int` is now stored as a float, so a sorted `Float` field also keeps one sort encoding. `True` was stored in an `Integer` field as `true` and indexed as `"True"`, where `count_by(field, 1)` did not find it.
- **A new `Database` on a persistent audit store keeps its counters** ([#19](https://github.com/smart-social-contracts/ic-python-db/issues/19), item 1). Each init reset `_min_id` and `_max_id`, so after an upgrade the next audit records overwrote the oldest ones; it also read the whole audit map to log its size. The counters are now written only when missing, and nothing is read.
- **A row stored by newer code is never overwritten.** After a rollback, the older code read a row of a higher `__version__`, ran `migrate()` with `from_version > to_version`, and saved it under its own, older version. Rolled forward again, the newer code migrated it a second time: a migration that is not idempotent applied twice (500 cents read as 50000). Such a row is now loaded as stored and never saved: a write to it raises `MigrationError`, and `deserialize()` refuses before it merges anything. Reads and listings work as before.
- **`serialize()` writes `__version__`, and `deserialize()` migrates the way `load()` does.** An export carried no version and an import took it to be version 1, so importing current data re-ran every step of `migrate()` on it (a v2 that renamed `description` to `manifesto` emptied the manifesto). A record without `__version__` is now taken to be of the current version, a record of a newer version is refused, and the others are migrated by the same code as `load()`: a `migrate()` that raises is a `MigrationError` naming the record, and defaults fill the fields it did not set.
- **Values `migrate()` sets are checked as a write checks them.** A row is built from storage without checks, and the save that persisted a migration did not check either, so a wrong value was stored (25 characters in a `String(max_length=5)`, text in an `Integer`), and the row then refused an ordinary write of that same value. A refused value is now a `MigrationError` naming the row and the field; text for a number is converted, as on a write. Values `migrate()` leaves alone are not checked.
- **A reference `migrate()` sets is linked on both sides.** A renamed (or added, or repointed) `ManyToOne` or `OneToOne` was saved in the row, but the other side reads the reverse index, which stayed as it was: `profile.user` and `team.members` found nothing. The migration now moves the reverse-index entry. Entries under a relation name the class no longer has stay, unread.
- **An alias value `migrate()` changes no longer leaves the old entry behind**, naming the row.
- **An entity that fails half-way through being built leaves the identity map.** The constructor registers an entity before setting its fields. In a canister the map keeps entities until the message ends, so after a listing skipped a row that could not be built (a value for a `OneToMany`, a `ManyToMany` naming a row that is gone), `page()` and `load()` of that id in the same message returned the half-built entity, with every field after the failing one missing. It surfaced when `test_migrations` first ran in a canister.

### Changed

- **What an `on_event` hook sees while a constructor runs:** `find_by` and `count_by` no longer list the entity being built, since its index entries are written after its row. The hook of an earlier field could see it there before.
- **The upgrade check refuses removing an entity type that has rows.** A renamed class passed as safe while the rows of the old name stayed stored and read by nothing. Basilisk runs this check in every canister's `post_upgrade` and traps when it raises, so such an upgrade is now rolled back. It is not waived by `migrate()`.
- **The schema records each type's `__alias__`**, and the upgrade check reports a moved alias as breaking (`ChangeType.ALIAS_CHANGED`), naming the rebuild to run. A removed alias is safe. Every stored schema hash changes once.
- `serialize()` output has a `__version__` key.

### Added

- `StaleEntityError`, in `ic_python_db` and `ic_python_db.errors`.
- `Entity.rebuild_alias_index(from_id, batch, old_alias)`: files rows under their alias value, in batches, like `rebuild_field_index`. After `__alias__` moves to another field, rows saved before are found by it once this has run; with `old_alias`, their entries under the old field are removed.

### Upgrading from 0.16

1. A schema stored by 0.16 records no alias, so the first upgrade to this version reports no alias change. If an alias moved in that same upgrade, run `rebuild_alias_index(old_alias=...)` for the type anyway.
2. Code that wrote to rows after a rollback now gets `MigrationError`. Roll forward, or migrate those rows' data back by hand.
3. A `migrate()` that set a value its field refuses now raises `MigrationError` on load. Before, the value was stored.
4. Tests that compare `serialize()` output to a dict need the `__version__` key, and tests that compare a stored schema need `alias` in each type.
5. `set_owner` is refused unless the caller owns the entity, and it saves. Code that handed an entity over by switching to the new owner, calling `set_owner` and writing must call it as the current owner instead. Code that never sets a caller saves as `"system"` and is not affected.
6. `set_caller_id`, `as_user` and `set_owner` raise `ValueError` for `None`, `""` or a value that is not a string. Check a caller id that may be missing (an optional argument, a failed lookup) before setting it.
7. `deserialize()` ignores `owner`, `creator`, `updater`, `timestamp_created` and `timestamp_updated` on a class with `TimestampedMixin`. An import that relied on them to restore who wrote a row now records the caller instead.
8. A write or delete by a caller who is not the owner raises `PermissionError` before the `on_event` hook runs. A hook that refused such callers itself (raising `ValueError("Hook rejected ...")`) no longer sees them; catch `PermissionError`.
9. **Index the rows that hold a default.** Rows saved before this release that hold the default of an indexed or sorted field are still missing from its index. For each type with such a field, run `rebuild_field_indexes` and `rebuild_sorted_index` until they return `None`, in calls of `batch` rows, as for any other rebuild. Until then those rows are missing from `find_by`, `count_by`, `page_by` and `top_by`, as they were before. (realms-gos's `Row` already files its field indexes, defaults included, from creation: for its types only `rebuild_sorted_index` adds anything, and the re-indexing in `Row.__init__` is now redundant and harmless.)
10. Creating or renaming a row to an alias value another row holds raises `ValueError`. Code that relied on the newest row taking the alias over must look the row up first (`Type[value] or Type(...)`). Duplicates stored before this release stay as they are, with the entry naming the newest of them.
11. Code that holds an entity across an `await` (a call to another canister) and writes it afterwards gets `StaleEntityError` if another message changed or deleted that row meanwhile. Load the entity again after the call, or catch `StaleEntityError`, reload and redo the change.
12. `Integer` and `Float` fields refuse `True` and `False`, and a `Float` field stores an `int` as a float.

## 0.16.0

### Fixed

- `TimestampedMixin` no longer loses its owner when a row is loaded. The mixin keeps its state in `_owner`, `_creator` and `_updater`, and stores it under `owner`, `creator` and `updater`. A load assigned the stored names as plain attributes and left the underscore ones at their initial values, so an entity loaded from storage (in a canister, every entity in a message after the one that created it) had no owner and `Entity._save` checked nothing: a caller other than the owner could write it, and the row did not record who had, because the stored `timestamp_updated` and `updater` overwrote the new ones on each save. The state is now restored on load, the check holds, and a save writes its own `updater` and `timestamp_updated`. The stored `timestamp_created` is written back as it was stored, as before; the stored text is never read as a time, so it does not matter that a canister's `datetime` cannot write one.
- The save that persists a migration when a row is loaded is not a write by the caller: it does not check the owner, and it leaves `updater` and `timestamp_updated` as stored. (With the check restored on load, a reader who did not own a row that needed migrating would have been refused.)
- A row stored before its class had the mixin, or by an earlier release of this library, loads as before. A row with an owner keeps it; a row without one is claimed by the first caller to save it, as it was (a read that migrates it does not claim it).
- A row whose `migrate()` raises no longer disappears from listings. `load_some` and `page` skipped a row that raised `ValueError` or `AttributeError` while it was built, which was meant for rows with a broken relation but also caught the error of `migrate()`. A bug in a `migrate()` left the rows counted by `count()` and missing from `load_some`, `page`, `instances` and `find`, with a warning in the log as the only trace, while `load()` of the same row raised.
- A custom `_id` that already exists is refused at the top of the constructor, before anything is written. It used to be found after the first argument had set its index entries, which stayed behind under the existing row's id. An argument that is refused later no longer leaves the type's count raised by the arguments before it (the id counter and the index entries of those arguments are still left behind: [#43](https://github.com/smart-social-contracts/ic-python-db/issues/43)).
- `deserialize()` of an existing row checks the owner before it merges any field. A caller who is not the owner of a `TimestampedMixin` row was refused only by the first field's save, after that field's hook had run and its index entry had moved; now nothing runs and nothing moves.

### Changed

- **A listing that returned a partial result now raises.** `load_some`, `page`, `instances`, `find` and the index rebuilds raise `MigrationError` when the `migrate()` of a stored row raises, the way `load()` does. A row that cannot be built because of a relation is still skipped with a warning: one that carries a value for a `OneToMany`, or whose `ManyToMany` list names a row that is gone.
- **`load()` raises `MigrationError` for such a row, no longer the error `migrate()` raised.** The message names the row (`Cfg@1`) and the versions it was migrated between, and the original error is its `__cause__`. Code that caught that error from `load()`, or from anything else that loads a row (`Entity[id]`, `find_by`, `top_by`, a relation's getter, iterating or paging a `RelationView`, the lookup `deserialize()` does to find the row to update), must catch `MigrationError`.
- **Cheaper reads and writes of entities.** Measured in a canister (basilisk 0.15.1 template, instructions): a cold `Listing` load (8 fields) 1.43M to 0.39M, `page(50)` 67.6M to 16.0M, `instances()` over 300 rows 403.6M to 93.4M, creating a `Listing` (8 arguments, 3 indexed, 1 sorted) 11.1M to 4.2M, creating a 4-field entity 4.85M to 1.36M, updating one plain field 1.02M to 0.44M.
  - The imports `Property.__set__` and the relation setters ran for each field of each entity they built are now at module level. In a canister each costs about 64,000 instructions, 128,000 of the 138,000 a field cost to load.
  - The lists of a class's fields that `save`, `find_by`, `count_by` and `delete` walked the whole class hierarchy for (properties, foreign keys, indexed properties) are computed once per class, on first use, as `_sorted_indexes` already was. They read the class as it is when first used.
  - The constructor no longer saves the row after each argument. It read storage and serialised the row for each one, and threw the result away, since saving is off until the constructor ends: 8 reads for a `Listing` with 8 arguments. The row is saved once, at the end. Hooks run, and index entries and audit records are written, as before. What an `on_event` hook sees while the constructor runs differs: `count()`, `_owner` and `_timestamp_created` are set only by that last save, no longer after the first argument.

### Added

- `MigrationError`, in `ic_python_db` and `ic_python_db.errors`.

### Upgrading from 0.15

1. Catch `MigrationError` where you caught the error your `migrate()` raises: from `load()`, and from anything that loads a row (see Changed).
2. Listings raise on a row whose `migrate()` raises. Under 0.15 such a row was missing from `load_some`, `page`, `instances` and `find`, and the log said `Skipping <Type>@<id>: <error>`. Look for that line, and fix the `migrate()` before you upgrade.
3. If your code sets a caller (`set_caller_id`, `as_user`) and uses `TimestampedMixin`, a save of a loaded entity by a caller who is not its owner now raises `PermissionError`, as it already did on the instance that created it. Code that never sets a caller saves as `"system"` and is not affected.
4. From 0.14 or earlier, also follow "Upgrading from 0.14" below.

## 0.15.0

### Fixed

- A field-index value that ends like an index key (`V1|n0000000000`) no longer hides other values' records. Its count key sat among the entries of `V1`, the page read of `V1` came back short, and `find_by` and `RelationView.page`, which take a short page for the last one, stopped: every id after it was unreachable. Any writer of a value could do it.
- A range read of a posting list goes on past keys that are not entries of its list (it already did in `_ix_all` and the purge; `_ix_page` stopped). It restarts at the last key it read instead of at the next char, which is not the next key for U+007F, U+07FF and U+FFFF, has no successor for U+10FFFF, and is a surrogate that cannot be encoded for U+D7FF.
- The entry of a custom id that reads as a JSON list is no longer taken for a list stored before 0.13 and removed.
- A store written before 0.13 that holds the lists of both a value `V` and `V|c`, `V|d`, `V|n` and 12 digits, or `V|h` and 24 hex digits no longer makes every read and write of `V` fail. The bare key of such a value is where later releases keep V's count (`|c`), mark (`|d`) or an entry (`|n…`, `|h…`), so reading V's count raised `ValueError` on the other value's array, an entry key listed that array's text as an id, and a write to V could replace it. A key of V's own that holds another value's old list now has that list converted first (which moves it out of the way), an entry counts only if it holds the id its key spells, and the repair no longer stalls on it.

### Changed

- **Field-index keys.** A value with a `|` in it is filed under `_fx:<Type>:<field>:<escaped value>` (`|` as `%7C`, `%` as `%25`), not under `_fi`. Every other value keeps its key, byte for byte: nothing moves for them, a value with only a `%` in it included.
- While entries of such a value may be under the old key, each `field_index_*` call also reads it, `field_index_add` and `field_index_remove` take the id off it, and a merged `field_index_get` / `field_index_page` lists an id once.

### Added

- `Database.repair_field_indexes(after="", limit=500)`: walks the field-index keys (of any length), in bounded calls. For values with a `|` it moves old entries to their present key, removes those whose entity is gone or has another value, and converts a list a release before 0.13 stored as one array.
- `Entity.rebuild_field_indexes(from_id, batch)`: `rebuild_field_index` for every indexed field of a type at once. `rebuild_field_index` moves old entries too.

### Upgrading from 0.14

1. Upgrade. Nothing is wrong meanwhile: values without a `|` are untouched, and those with one are read under both keys.
2. Run `Database.repair_field_indexes` until it returns `None`, in calls of `limit` keys. This moves every old entry, custom ids included, and converts old-form lists of values with a `|`; nothing needs to run before it (`rebuild_field_indexes` is optional). Correctness does not wait for it; it is what lets a later release drop the old-key reads, once it has run to its end. It leaves what it cannot judge: entries of a type or field the code does not index; entries whose row has no such field; an old-form list of more than 100 thousand ids (logged; a read of its value converts it where it fits the message, about 160 thousand ids in an update and 20 thousand in a query, and traps where it does not, as before); and an old-form list of a value made to end with `|h` and the digest of its own text, which reads as an entry of the value it extends (only such a value matches; `find_by` is not affected). Known limit: a chain of old lists of `V`, `V|c`, `V|c|c` and so on deeper than about 500 raises `RecursionError` (also a value made for it). Cost, measured on the IC: a key read about 0.1 million instructions; a right entry of a value with a `|` about 0.73 million; an old entry moved about 2 million (a call of 500 moves is about 1 billion); about 0.58 million for each distinct key length in the whole map that a call walks past, so a call is O(`limit` + those lengths); an old-form list is converted whole at about 245 thousand an id, and a realm's map is not limited in value size (a list of 127,000 ids is on record: about 31 billion; it is over the cap of 100 thousand ids, so the repair leaves it, and a read of its value in an update converts it).
3. If 0.13 or 0.14 already ran on a store of 0.12 that holds the old lists of both a value `V` and `V|n` and 12 digits, or `V|h` and the digest of a custom id in `V`'s list, converting `V` wrote its entry over the other value's old list: that value's ids are lost. `Entity.rebuild_field_indexes` re-adds the sequential ones (run it, then the repair); a custom id comes back only when its entity's field is next changed, or when `Database.field_index_add` is called for it.
4. A realm that escapes its own values before indexing them (realms-gos tags: `%` as `%25`, `|` as `%7C`) holds no `|`: its keys do not change. It can keep doing so.

### Rolling back to a release before 0.15, and upgrading again

While the older release runs, a value with a `|` is filed under `_fi` (0.15 reads it there), but entries 0.15 filed under `_fx` are invisible to it, and it does not remove an `_fx` entry when an entity's value changes or the entity is deleted. After the next upgrade `count_by` and `find_by` can be wrong for such values (an entity listed that no longer has the value, an id on both lists). Run `Database.repair_field_indexes` until it returns `None`, **starting again from `after=""`** (a cursor, or a note that it was done, saved before the rollback skips what the older release wrote): it removes what is stale, moves what the older release filed, and the counts are exact again.
